# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test Commands

```bash
# Build the entire package
swift build 2>&1 | xcsift

# Build a specific target
swift build --target FoundationToolbox 2>&1 | xcsift

# Run tests
swift test 2>&1 | xcsift

# Run a specific test
swift test --filter FrameworkToolboxTests 2>&1 | xcsift

# Run a macro client for manual testing
swift run FoundationToolboxClient 2>&1 | xcsift
```

Always pipe `swift build` / `swift test` output through `xcsift`.

## Project Overview

FrameworkToolbox is a Swift Package (Swift 6.2, language mode Swift 5) providing layered libraries of utilities and Swift macros:

**Dependency chain:** `FrameworkToolbox` <- `OSToolbox` <- `SwiftStdlibToolbox` <- `FoundationToolbox`

`CoreFoundationToolbox` depends on `FrameworkToolbox`; `DyldToolbox` depends on `OSToolbox`. `ObjCRuntimeToolbox` deliberately depends on no runtime target at all — see its row below. `SwiftStdlibToolbox` depends on `DyldToolbox` purely to re-export it — nothing in its own sources touches interposing.

| Library | Purpose |
|---------|---------|
| `FrameworkToolbox` | Core "box" pattern (`FrameworkToolbox<Base>`) with `@dynamicMemberLookup` for namespaced extensions via `FrameworkToolboxCompatible` protocol. Also the single definition of `AccessLevel` |
| `OSToolbox` | Everything layered directly on Apple's `os` module: `Mutex`, `WeakBox`, `SignpostInterval`, `LoggingControl` / `SignpostingControl`, and the macros `@Mutex`, `@OSAllocatedUnfairLock`, `@Loggable`, `#log`, `@Signpostable`, `#signpost`, `#signpostInterval`. Depends on `os` and the stdlib only — no Foundation anywhere, which is why `@Loggable`'s default subsystem is the type name rather than a bundle identifier |
| `SwiftStdlibToolbox` | Swift stdlib extensions + macros (`@Equatable`, `@AssociatedValue`, `@CaseCheckable`, `@AvailableNonMutating`, `@AvailableMutating`, `@AddAsync`, `@AddAsyncAllMembers`, `@AddCompletionHandler`) |
| `DyldToolbox` | dyld interposing: the macros `@DyldInterpose` / `@DyldDynamicInterpose` plus the `DyldDynamicInterpose` runtime. Split out of `SwiftStdlibToolbox` so that a consumer wanting only the binary-level hooks does not link the Swift-extension layers above it — and so that consumers of *those* layers no longer link the arm64e C shim only these hooks need. Sits on `Darwin` / `MachO` / `PointerAuthenticationSupport` plus `OSToolbox` (for `Mutex`). Must stay a **static** library — see the note under "Interposing macros" |
| `FoundationToolbox` | Foundation extensions + macros (`#url`, `#selector`-style, `@Keychain`, `@UserDefault`), `NSLock`-based wrappers, shared `Storage` layer (Keychain + `UserDefaults`), and the typed Objective-C collection handles (`NSArrayOf` and its five siblings) |
| `CoreFoundationToolbox` | CoreFoundation wrappers, toll-free bridging, Mach error types (adapted from SwiftCF) |
| `ObjCRuntimeToolbox` | Objective-C runtime: method hooks, isa-swizzling (`DynamicSubclass`), runtime proxies, and `DynamicObject`/`ObjC` for calling classes with no header. Built as a `.dynamic` product so its process-wide runtime state stays a single copy. The target must stay macro-only: Xcode builds a `.dynamic` product's transitive targets as shared dynamic frameworks for the whole workspace, which is how 0.10.0's `OSToolbox` dependency broke rpath-less nested executables (guarded by `PackageTopologyGuardTests`; see `Documentations/Evolutions/0003-objc-runtime-toolbox-self-contained-leaf.md`) |

`PointerAuthenticationSupport` is a C target backing `DyldToolbox`'s `@DyldDynamicInterpose`, not a library product.

**Re-export chain — important when moving code between these targets.** `OSToolbox` re-exports `FrameworkToolbox` and `os`; `SwiftStdlibToolbox` re-exports `OSToolbox` **and `DyldToolbox`**; `FoundationToolbox` re-exports `SwiftStdlibToolbox`, `Foundation` and `Combine`. Off to the side, `CoreFoundationToolbox` re-exports `FrameworkToolbox` and `CoreFoundation`, and `ObjCRuntimeToolbox` re-exports `Foundation` and `ObjectiveC`. That is why `import FoundationToolbox` alone resolves `@Mutex`, `@Loggable`, `AccessLevel`, `os.Logger`, and `@DyldInterpose`.

The three non-chain re-exports are **not** conveniences; each fixes a call site that did not compile. Their reasons are in the respective `Exported.swift`, and the short version is: `#URL`/`#Selector` expand to Foundation (`URL(string:)!`, `NSSelectorFromString(_:)`), every `ObjCRuntimeToolbox` macro expands to `NSSelectorFromString(_:)`, and 59 `CoreFoundationToolbox` declarations spell `FrameworkToolbox<…>` out in the open — including every `allocator: CFAllocator = FrameworkToolbox<CFAllocator>.default` default argument. `@_exported import` carries macro declarations *and* their plugins across transitive dependencies, so a macro can be moved into another target without breaking any existing call site — see `Documentations/Specs/2026-08-06-ostoolbox-extraction-design.md` and `Documentations/Evolutions/0001-dyld-toolbox-extraction.md`.

A re-export is invisible in the sense that nothing fails when it breaks — no test covers "the old import path still works". Both extractions therefore pin it at compile time from a client target: `Sources/OSToolboxNoFoundationClient/` for the `OSToolbox` split, and the `DyldToolbox re-export` section at the end of `Sources/SwiftStdlibToolboxClient/main.swift` for this one. The signpost macros pin both hops the same way — `SwiftStdlibToolboxClient` (one hop) and `FoundationToolboxClient` (two hops). Keep that pattern when moving anything else down a layer.

The three `*SoleImportClient` targets (`FoundationToolboxSoleImportClient`, `ObjCRuntimeToolboxSoleImportClient`, `CoreFoundationToolboxSoleImportClient`) are the same idea aimed the other way: **no file in them may import anything but the one product under test**, so they fail the moment a macro expansion or a public signature reaches for a module the caller never asked for. Each was written against a real failure and verified to still fail when its re-export is commented out — a guard nobody has watched break is not a guard.

**`OSToolboxNoFoundationClient` is a whole target dedicated to one guard: no file in it may import Foundation.** It has to be a target of its own, not a file inside `OSToolboxClient`, because **Swift resolves protocol conformances module-wide rather than per file** — one `import Foundation` anywhere in a target hands `String: CVarArg` to every file in it, however carefully an individual file avoids the import. That is exactly how the `#log` legacy-branch defect survived: the guard sat next to a `main.swift` that imported Foundation.

## Architecture

### Macro System

Each library has a corresponding macro target (`*Macros`). A shared `MacroToolbox` target provides reusable protocols for lock-style macros (`LockMacroProtocol`, `LockPropertyParser`) — `DyldToolboxMacros` deliberately does not depend on it, since none of that machinery applies to interposing. `MacroToolbox` depends on `SwiftSyntaxBuilder` explicitly even though `SwiftSyntaxMacros` would drag it in: `LockPropertyParser` builds syntax from string literals (`ExprSyntax("nil")`), and relying on the transitive path is the kind of undeclared dependency Xcode 27's `VALIDATE_DEPENDENCIES` reports.

Macro targets depend on `swift-syntax` (509.1.0..<604.0.0). Each macro plugin is a `CompilerPlugin` entry point registering its macros.

Executable client targets (`*Client`) exist for manual macro expansion testing.

### Key Patterns

- **Box pattern:** `FrameworkToolboxCompatible` conformance gives any type a `.box` accessor returning `FrameworkToolbox<Self>`, enabling namespaced extensions without polluting the type's API surface.
- **Lock macros:** `@Mutex`, `@OSAllocatedUnfairLock` share logic via `LockMacroProtocol` in `MacroToolbox`. They generate a backing stored property and computed accessors with lock/unlock around access.
- **Available storage macros:** `@AvailableNonMutating` and `@AvailableMutating` generate `Any?` backing storage plus lazy accessors for `@available`-gated properties whose storage cannot mention the gated type directly. The mutating variant also emits a setter.
- **Logging:** `@Loggable` generates `category`/`subsystem`/`_osLog`/`logger` properties. `#log` emits version-checked code that uses `os.Logger` on macOS 11+ or falls back to the legacy `os_log` API with per-segment privacy support. `@Loggable` also always generates `logger(for:)`/`_osLog(for:)` accessors taking the library `LogCategory` struct (`OSToolbox/LogCategory.swift`), cached per subsystem/category pair in `Loggable.swift`. Users declare categories as static members (`extension LogCategory { static let network = LogCategory("network") }`, the `Notification.Name` pattern) and select one per call site via `#log(.debug, category: .network, ...)` — the macro transplants the category expression verbatim into the expansion, so leading-dot references get real autocomplete and call-site type checking.
- **Turning logging and signposting off:** `@Loggable(isEnabled:)` and `@Signpostable(isEnabled:)` default to `true`. The switch lives on the *handle*, not the call site, because `#log` / `#signpost` are freestanding macros and cannot see what the enclosing type's `@Loggable(...)` was given — macros have no channel between them. So a disabled type's `logger` / `_osLog` / `signposter` / `_signpostLog` simply hand back `Logger.disabled` / `OSLog.disabled` / `OSSignposter.disabled`, which silences `#log`, `#signpost`, and any hand-written `Self.logger.debug(…)` at once, with `LogMacro.swift` and `SignpostMacro.swift` untouched. **A disabled handle does not evaluate the message's interpolation arguments at all** — in `os`, `osLogInternal`'s `guard logObject.isEnabled(type:)` and `osSignpost`'s `guard log.signpostsEnabled` both sit ahead of `argumentClosures`, and those closures are `@autoclosure`. That ordering is the whole basis of the design, so `DisabledLoggingSkipsInterpolationTests` pins it with an evaluation counter and goes red if a future SDK moves it. Three switches are ANDed: the macro argument, `LoggingControl.isEnabled` / `SignpostingControl.isEnabled`, and the per-category `setEnabled(_:for:)`. The macro argument is read as syntax, so a **boolean literal** collapses to a compile-time constant (`isEnabled: false` emits no storage at all and cannot be re-enabled at runtime) while **any other expression** is transplanted verbatim and `&&`-ed with the runtime check — one spelling covering both "strip it from the build" and "gate it on my own flag". Logging and signposting have separate controls on purpose: "logs on, instrumentation off" and the reverse are both wanted. Since a type with no explicit `category:` uses its own name, `LoggingControl.setEnabled(false, for: LogCategory("SyncService"))` silences one type without recompiling. The two `Bool`s behind the global switches are `nonisolated(unsafe)` rather than `Mutex`-guarded — every call site reads them, a single-byte load cannot tear, and the per-category set is only consulted after a `hasDisabled…` flag says someone actually disabled something. Design and the alternatives weighed: `Documentations/Evolutions/0004-logging-enable-switch.md`; caller-facing usage: `Documentations/LoggingSwitches.md`.
- **`@Loggable` / `@Signpostable` work on generic types**, which they did not before: they used to generate `static let`, and Swift permits no static stored properties in a generic type — *including in a non-generic type nested inside one*. The concrete branch therefore has two shapes. Outside a generic context the live handle stays in a `static let` (unchanged cost); inside one it comes from the same metatype-keyed runtime cache the protocol branch has always used, so the generic support needed no new runtime code. Detection reads the declaration's own `genericParameterClause` **plus `MacroExpansionContext.lexicalContext`** for the enclosing chain — the nested case is invisible in the declaration's own syntax tree. An enclosing `extension` is treated as restricting whatever it extends, since `extension Box` cannot tell you whether `Box` is generic; a needless cache lookup costs nanoseconds, a wrongly emitted `static let` costs a compile error in the caller's file. `lexicalContext` is why swift-syntax's floor is `600.0.0`. Generic types share one category (`Box<Int>` and `Box<String>` are both `"Box"`) because `staticTypeName` reads the syntactic name — deliberate, so `log stream` predicates stay writable.
- **Async bridging macros:** `@AddAsync` generates an `async` overload of a completion-handler function; `@AddCompletionHandler` generates the reverse; `@AddAsyncAllMembers` applies `@AddAsync` to every member of a type. `@AddAsync` and `@AddAsyncAllMembers` share `AddAsyncMacroCore`. All three are raw `swift-syntax`; the signature-rewriting helpers they need (`withAsyncModifier`/`withThrowsModifier`/`withParameters`/`withReturnType`/`withBody`/`withAttributes`, `asPassthroughArguments`, and the `isVoid` / `Result<Success, Failure>` type checks) live in `SwiftStdlibToolboxMacros/AsyncBridgingSupport.swift`.
- **Interposing macros:** `@DyldInterpose` and `@DyldDynamicInterpose` expand to the same `(replacement, replacee)` tuple of `@convention(c)` pointers — dyld's `dyld_interpose_tuple` layout — and share all parsing, validation and code generation via `DyldToolboxMacros/DyldInterposeSupport.swift`; a `DyldInterposeExpansionConfiguration` is the only difference. `@DyldInterpose` targets `__DATA,__interpose`, which dyld consumes at load time (dylib only, irreversible). `@DyldDynamicInterpose` targets a private `__DATA,__dyn_interpose` that dyld ignores; the `DyldDynamicInterpose` runtime (in `DyldToolbox/DyldInterpose/`) reads it back via `getsectiondata(#dsohandle, …)` and rewrites symbol pointer slots on demand — this revives `dyld_dynamic_interpose`, an empty function since dyld4 (`rdar://74287303`), by reproducing dyld2's `ImageLoaderMachOClassic::dynamicInterpose`. It works from a main executable, is revertible, and only reaches `S_NON_LAZY_SYMBOL_POINTERS` / `S_LAZY_SYMBOL_POINTERS` slots. The C target `PointerAuthenticationSupport` supplies the arm64e strip/sign intrinsics Swift cannot spell, and is a no-op elsewhere. Design and measured limits: `Documentations/Specs/2026-08-06-dyld-dynamic-interpose-design.md`; the extraction into its own target: `Documentations/Evolutions/0001-dyld-toolbox-extraction.md`.
- **`DyldToolbox` must stay a static library.** Every `declaredIn:` parameter defaults to `#dsohandle`, and a default argument is evaluated at the *call site* — so "which image's `__DATA,__dyn_interpose` gets read" follows whoever calls `applyAll()`, not wherever `DyldDynamicInterpose` happens to be compiled. That is the property that survived moving this code between targets, and it is why the product is deliberately *not* `.dynamic` the way `ObjCRuntimeToolbox` is. There is a real trade-off here: the `revertAll()` bookkeeping is per-copy, so one statically-embedded image cannot undo another's rewrites. That is accepted, not overlooked — "whoever declares, applies, and reverts" is already an image-scoped model. Changing it is a behavior change, not a packaging tweak.
- **Signposting:** `@Signpostable` is the signpost counterpart of `@Loggable` — same attribute grammar, same concrete/protocol split, and the two are meant to be applied together, so **none of their generated member names overlap** (`signpostSubsystem`/`signpostCategory`/`_signpostLog`/`signposter` versus `subsystem`/`category`/`_osLog`/`logger`). That is a hard constraint: two member macros emitting one name is an `invalid redeclaration`, pinned by `DualAnnotatedService` in `Sources/OSToolboxNoFoundationClient/`. `#signpost` has three forms — `.event` (a point in time), `.begin`/`.end` (an interval spanning calls), and `#signpostInterval(_:) { … }` (an interval scoped to a closure, with the end in a `defer` so it closes on every exit path, thrown errors included). All expand to `OSSignposter` on macOS 12 / iOS 15 / watchOS 8 / tvOS 15 and up, `os_signpost` below. Three points that are not obvious from the code:
  - **`SignpostInterval` (`OSToolbox/SignpostInterval.swift`) exists because `OSSignpostIntervalState` is gated at macOS 12**, so it cannot be the type of a property on this package's macOS 10.15 floor. It carries the gated state behind an `@available` accessor — the same shape `@AvailableNonMutating` produces — plus the name and, critically, **the `OSLog` the interval began on**. The system pairs a begin with an end by handle, name and signpost ID, and `OSLog(subsystem:category:)` hands back a fresh object per call with no promise that two share an underlying handle. Re-deriving the handle at the end would therefore risk intervals that never match up; carrying the reference removes the question and makes `#signpost(.end, …)` self-contained (usable from a type that is not itself `@Signpostable`).
  - For the same reason, `_sharedSignposter` builds `OSSignposter(logHandle:)` over the cached log handle and **never** `OSSignposter(subsystem:category:)`, which would create a second handle for one subsystem/category pair.
  - **`#signpostInterval` splices the body in exactly once**, outside the `#available` branching (the branching lives inside the generated begin and end). Putting the body in both branches would compile the measured code twice. It also inserts no `try`/`await` of its own — the body's own effects are in the spliced text, so the compiler infers them and the call site spells them as the body demands. This is why the macro needs both a sync and an `async` body overload: a macro declaration is type-checked like a function, so an `async` closure will not bind to the sync one.
- **The three system signpost categories are on `LogCategory`**: `.pointsOfInterest`, `.dynamicTracing`, `.dynamicStackTracing`, spelled exactly as `os/signpost.h` defines them (a typo does not fail, it silently produces an ordinary category — hence a test asserting the strings). Only `pointsOfInterest` has an SDK counterpart in Swift. Verified live: signposts under `.pointsOfInterest` land in that category, and **`.dynamicTracing` ones do not appear in `log show` at all** — that category is disabled unless a tool like Instruments is recording, which is its documented purpose rather than a fault.
- **Dynamic invocation:** `ObjCRuntimeToolbox/DynamicInvocation/` provides `DynamicObject` (aliased `ObjC`) for calling classes and methods that have no header, via `@dynamicMemberLookup` + `@dynamicCallable` over `NSInvocation`. Adapted from [mhdhejazi/Dynamic](https://github.com/mhdhejazi/Dynamic) under Apache 2.0 (`LICENSES/Dynamic-LICENSE`). Two rules matter when editing it: every `unsafeBitCast` to a `@convention(c)` signature lives in `NSInvocationBridge.swift` so the signatures can be reviewed as a set, and an object return must be spelled `AnyObject?` — `Any?` compiles fine and corrupts memory, because it is a 32-byte existential container rather than an `id`-sized pointer. `DynamicObject` and `RuntimeInvocation` log through one shared hand-written handle (`dynamicInvocationLog`, subsystem `ObjCRuntimeToolbox`, category `DynamicInvocation`) — the same pair on purpose, so one `log stream` predicate covers the whole path. Deliberately not `@Loggable`: the target must not depend on `OSToolbox` at runtime (see the `ObjCRuntimeToolbox` row above). See `Documentations/Specs/2026-08-06-dynamic-invocation-design.md`.
- **`@Loggable` on a `@dynamicMemberLookup` type is safe** (verified, not assumed). `@Loggable` emits its members `private`, and private members are excluded from the member lookup that dynamic member lookup falls back from — so `logger`/`_osLog`/`subsystem`/`category` stay forwardable to Objective-C from outside the type, while `#log` still resolves `Self.logger` inside it. What *does* shadow is any member visible to the caller: `public` members, and protocol-extension members (statically dispatched, so the compiler binds them before dynamic lookup gets a chance). Adding a protocol layer does not avoid this — visibility is what decides, not where the member comes from.
- **`#log` inside an instance method needs explicit `self.`** on any interpolated property. The macro expands to an immediately-invoked closure, so `\(debugDescription)` fails to compile while `\(self.debugDescription)` works.
- **A macro must not expand to code naming a module the caller may not have imported.** `@Loggable`'s default subsystem used to expand to `Bundle.main.bundleIdentifier ?? "…"`, which fails with `cannot find 'Bundle' in scope` in any file that skipped `import Foundation` — and the error points at generated code the source never mentions. Wrapping the *generated* code in `#if canImport(Foundation)` does not fix it: `canImport` reports whether a module could be imported (always true for Foundation on Apple platforms), not whether this file imported it. Either drop the dependency (what `@Loggable` did — the default subsystem is now just the type name) or move it into a runtime helper inside the macro's own module. `Sources/OSToolboxNoFoundationClient/` guards this at compile time. **A conformance counts as such a dependency too**, and that is the subtler case: `#log`'s legacy branch used to expand to `os_log(…, "%{public}@", "\(value)")`, and `String: CVarArg` comes from Foundation — the standard library has none — so any interpolated message failed to compile in a module that never imported it. It now passes each segment as `UnsafePointer<CChar>` via `String.withCString`, both standard library.

  This defect class was later swept across every macro target, and it had spread: `#URL`, `#Selector`, `@RuntimeClassProxy`, `@RuntimeClassHook`, `@RuntimeMethodReplacement` and `@DynamicSubclassHook` were all reaching Foundation from their expansions. Those were fixed by **re-exporting** rather than by dropping the dependency, which is the right call when the target's whole purpose is that module (see the re-export chain above) — dropping it is only right when the dependency is incidental, as `Bundle` was to `@Loggable`. Two things are worth carrying forward. First, **sweep the whole class, not the one reported site**: the rule had been written down here after the `@Loggable` fix but never applied to the other targets. Second, **a name collision is a possible failure mode, not just a missing symbol**: with Foundation absent, the `URL` inside `#URL`'s expansion resolved to `FoundationToolbox`'s own `URL` *macro*, and the compiler reported `expansion of macro 'URL' requires leading '#'` — an error about an entirely different `URL`, with nothing in it pointing at the real cause.
- **Availability macros are a per-target setting, so they must not escape the target.** `Package.swift` defines the `SwiftStdlib X.Y` names upstream uses (same table as the standard library, swift-foundation and swift-testing) and injects them into all 39 targets through a loop, so a gated declaration reads `@available(SwiftStdlib 5.7, *)` rather than spelling four platform versions out. Anywhere the code gets recompiled in *someone else's* compilation unit, the setting is absent and the name does not resolve. Two such places. **`@inlinable` / `@_transparent` bodies** — the compiler rejects it outright (`availability macro cannot be used in an '@inlinable' function`), which is how `FrameworkToolbox<String>.filePathURL` was caught; it keeps the long form with the reason noted in place. **Macro expansions** — `LoggableMacro.loggerAvailability` and `SignpostableMacro.signposterAvailability` build `@available(...)` as text, and that text lands in the caller's file. The second one is the dangerous half: **the compiler gives no diagnostic at all**, this package builds clean, and the failure surfaces in a downstream module pointing at generated code their source never mentions — the same failure mode as a macro expanding to code that names an unimported module, wearing a different coat. Only `SwiftStdlib 5.7` is in use so far; the 19 remaining long-form sites gate `os.Logger` and `OSSignposter`, which track SDK capability rather than the standard library version line and would need their own semantic macros. See the `availability-macros` proposal.
- **`canImport(X)` is not a platform guard.** It answers "can this module be imported", not "does this symbol exist here", and Apple's umbrella frameworks are routinely importable-but-unavailable on derived platforms: `canImport(QuartzCore)` is true on watchOS where `CATransform3D` is unavailable, and `canImport(AppKit)` is true under Mac Catalyst where nearly all of AppKit is. Guard those with `os(...)` / `!os(...)`. Since `swift build` only covers macOS and these regressions are compile-time (no unit test can catch them), build every declared platform after touching a guard — the loop is in `Documentations/Specs/2026-08-06-dynamic-invocation-design.md`.
- **`os_log` treats string interpolations as private by default**, so an unannotated trace reads `call [<private> <private>]` and is worthless. The convention in `DynamicInvocation/` is to mark structural values (class names, selectors, member names) `privacy: .public` and leave payloads (wrapped-object descriptions, argument and return values) private, since those can carry arbitrary user data.
- **Typed Objective-C collection handles:** `FoundationToolbox/ObjectiveCCollections/` holds six generic structs — `NSArrayOf`, `NSMutableArrayOf`, `NSDictionaryOf`, `NSMutableDictionaryOf`, `NSSetOf`, `NSMutableSetOf` — putting the element type back on the Foundation classes Swift imports non-generically. That erasure is deliberate, not a gap: `shouldSuppressGenericParamsImport` in the compiler's `lib/ClangImporter/ImportDecl.cpp` drops the lightweight generics of `NSArray`, `NSDictionary`, `NSSet`, `NSOrderedSet`, `NSEnumerator` and `NSMeasurement` plus every subclass, and Foundation's API notes pair `SwiftBridge:` with `SwiftImportAsNonGeneric: true` on exactly those classes — the parameter is not lost, it moves to `[String]`. Three constraints are invisible in the code. **They must be structs**: `_ObjectiveCBridgeable` is only consulted for value types — `DynamicCast.cpp` reaches `tryCastFromObjCBridgeableToClass` only when the source is a struct or enum, and the reverse only when the destination is, while `_bridgeAnythingToObjectiveC` documents that a class type "is always bridged verbatim". A generic class wrapping `NSArray` would have the protocol skipped entirely and arrive at an `Any` parameter as a `_SwiftValue` box, which is the one thing these types exist to prevent. **They are reference semantics on purpose** — a handle wraps the collection rather than copying it, which is the whole point (KVC proxies, key-value observing, handing a mutable collection back to Objective-C and both sides continuing to write). That is why the mutating operations are deliberately not `mutating`, the subscript setters are `nonmutating`, and the mutable handles are not `Hashable`. **`as?` is not the spelling to reach for**: it works, and `ObjectiveCCollectionBridgingTests` pins in both debug and release builds that the element validation really runs, but the compiler classifies a cast from the exact `_ObjectiveCType` as an unconditional bridging coercion and reports `conditional cast ... always succeeds` at every such call site — so the API vends `init?(validating:)`, which is ordinary Swift with no cast machinery. Caller-facing contract and traps: `Documentations/TypedObjectiveCCollections.md`; design and the alternatives weighed: the `objective-c-typed-collections` proposal.
- **Storage layer:** `FoundationToolbox/Storage/` holds two parallel codec protocols shared across storage backends. `DataStorable` (used by Keychain) encodes `Self ↔ Data`; `PlistStorable` (used by `UserDefaults`) encodes `Self ↔ Any` (plist-compatible objects). The same primitive set — `String`, `Data`, `Bool`, the integer/floating-point families, `Date`, `URL`, conditional `Optional<Wrapped>` — conforms to both. `DataCodableStorable` / `PlistCodableStorable` are markers that let any `Codable` type opt into JSON-backed storage. A shared internal `_AnyOptionalStorableValue` hook detects `nil` writes so backends dispatch to their "delete" path.
- **Keychain macro:** `@Keychain(key:service:synchronizable:accessible:)` is an accessor + peer macro that turns a stored property into a Keychain-backed one. The generated peers are `private let _<name> = KeychainStorage<Value>(...)` and `var $<name>: some Publisher<Value, Never>` (opaque type hides the underlying `PassthroughSubject`'s `.send`). The `KeychainStorage` runtime (in `FoundationToolbox/Keychain/`) wraps `SecItem*` directly — no third-party Keychain dependency. `KeychainStorable` / `KeychainCodableStorable` are typealiases of the shared `DataStorable` / `DataCodableStorable`.
- **UserDefault macro:** `@UserDefault(key:suite:)` mirrors `@Keychain` but persists to `UserDefaults`. Generated peers are `private let _<name> = UserDefaultStorage<Value>(...)` plus `var $<name>: some Publisher<Value, Never>`. The `UserDefaultStorage` runtime (in `FoundationToolbox/UserDefault/`) uses `set(_:forKey:)` / `object(forKey:)` for plist-native primitives, calls `removeObject(forKey:)` when an `Optional` value is written as `nil`, and subscribes to `UserDefaults.didChangeNotification` so the publisher also reflects writes made externally (system Settings.app, another piece of code in the process, another process targeting the same suite). A `suppressNextNotification` flag avoids double-publishing the value written through `set(_:)`. `UserDefaultStorable` / `UserDefaultCodableStorable` are typealiases of the shared `PlistStorable` / `PlistCodableStorable`.
